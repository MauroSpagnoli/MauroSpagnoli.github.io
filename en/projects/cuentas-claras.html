CuentasClaras

Shared-expenses app: groups, flexible splits, balances and settlement with the minimum number of transfers.

The problem

Splitting a flat's expenses looks trivial and is not. You need to know who paid for what, decide whether an expense is split equally, by exact amounts or by percentages, allow someone to jot something down on the underground with no signal, and then close the month without an endless round of transfers.

The silent enemy is the cent. Most apps in this space turn money into floating point, and then €10 split three ways stops adding up to €10. Here, if the numbers do not add up to the cent, the app is wrong.

How I solved it

  • Money is always stored as integers (cents) and never goes through floating point. The split computes each share and hands out the remainder one cent at a time, so the parts add up to exactly the total.
  • The Android client is offline-first: every write lands in local storage first (Room), is queued in an outbox table and a SyncWorker sends it to the server. Each send carries its own identifier, so repeating one does not duplicate the expense.
  • The API is a Spring Boot service with JWT (access token and rotating refresh). The contract lives in an openapi.yaml versioned in the repository, and the integration tests spin up a real database with Testcontainers.
  • The balances screen shows each member’s net balance and proposes a settlement plan: the shortest list of payments that brings every account back to zero.

Decisions that hold the rest up

Money as integers, always
Storing cents avoids rounding errors. The split hands out the remainder unit by unit, so the parts add up to the total and no cent is left behind.
A single API contract
The openapi.yaml is the reference: the app, the tests and the documentation all point at the same file. If the contract changes, the review shows it.
The network is a detail, not a requirement
The interface never waits for a request: it writes locally and answers instantly. Syncing is a background job that can be retried without fear.
Idempotent retries
Every queued operation carries its own identifier. If a send is repeated —because the response was lost— the server recognises the operation and does not duplicate it.

What I would do next

  • Notifications when someone adds an expense to a shared group.
  • Exporting a group’s history to CSV for anyone who wants to review it outside the app.
  • A second accessibility pass over the split tables, which is the densest screen per row.
