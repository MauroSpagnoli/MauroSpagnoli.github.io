The problem

A to-do list is the sample app of almost every tutorial, and that makes it a good place for the opposite: showing how a small app is built so it can be maintained and tested. The interesting decisions are not on the screen —two lists and a dialog— but in where each piece lives.

Who decides what a task is? How is it stored? How do you test a use case that writes to disk without waiting on a real thread? And how do you change language without restarting the app by hand?

How I built it

  • Three layers (domain, data, UI) with dependencies pointing one way: the UI does not know about Room and the domain knows about nobody. Each layer has its own model and the mappings live at the boundary.
  • The use cases receive the CoroutineDispatcher by injection and return a Job. In production they get the I/O dispatcher; in tests, a TestDispatcher. That is why the tests are deterministic and nothing really waits.
  • Local persistence with Room (a todos table, version 1, schema exported to the repository) and the dependency graph with Hilt.
  • A Jetpack Compose interface: a pending section and a completed one, an add-and-edit dialog, a per-task menu (edit and delete) and a strike-through when a task is done.
  • Real Spanish and English, with per-language resources. The preference is stored in SharedPreferences and the Locale is applied in attachBaseContext, before composing, so there is no language flicker on start-up.
  • Automated quality: JUnit + MockK for unit tests, Robolectric for UI tests, and Detekt plus Android Lint in CI. Every push to main builds a signed APK and publishes it as a release.

Decisions that hold the rest up

Three layers, one direction
Each layer has its own model. The UI never sees database entities and the domain never sees an Android library. Swapping Room for something else would not touch the logic.
The thread is injected, not chosen
No use case decides which thread it runs on: it is given one. The tests hand it a controlled dispatcher and check the result without sleeping the process.
The language is set before composing
The stored Locale is applied in attachBaseContext, so the first screen already comes up in the right language, with no reload.
CI builds, analyses and publishes
Every push to main passes Detekt, builds the release variant and signs the APK. Static analysis is a gate, not a hint.

What I would improve

  • The “+” button in the “Completed” section creates the task as pending: the state is derived from the first item of the list (items.firstOrNull()?.completed) instead of the section. With the section empty there is no item to derive it from, so it falls back to pending. The header should receive its own state.
  • The accessibility labels of the bottom bar are written in the view rather than coming from the string resources, so switching language does not cover them. A small fix with a big payoff.
  • And two features I miss: a search box and drag to reorder.
